Proof of concept · design note

Planogram Locator Architecture

Search a product, see whether it is in stock, see which floor, aisle and rack it sits on, and get the optimal route to reach it — across a three-floor store.

Orchestration LangGraph Service FastAPI Frontend static HTML + SVG Data synthetic, in-memory JSON

1 · Where LangGraph sits

Five layers. The point of the drawing is the third one: LangGraph is the orchestrator, and every fact in a response is fetched by a deterministic service below it. The model never holds the data.

2 · The graph

Nine nodes. Six are ordinary Python functions, three call a model, one pauses for the shopper. That ratio is the design: LangGraph is here for state, branching and interrupts — not to let a model decide what happens next.

3 · Routing across three floors

Floors change the routing problem more than anything else in the brief. A distance-only optimiser will send a shopper up and down repeatedly, because it has no notion that a floor change is worse than the metres it costs. So the floor order is fixed and each floor gets one picking pass.

The rule: ride to the highest floor that has items, then work down, finishing at the ground-floor tills. Two cores — front and rear — mean each pass ends next to a lift, so the shopper never walks back the way they came.

4 · Decisions

Orchestration

LangGraph runs the whole pipeline, not only the AI parts

Deterministic steps become plain-function nodes. This costs nothing and buys two things: the generated graph is the architecture diagram, so it cannot drift from the code, and the UI can stream node-by-node progress — "found 3 products → checking stock → planning route across 2 floors".

The risk to name out loud is the opposite one. Search → availability → location → route is a fixed sequence, so a ReAct-style agent that decides which tool to call next would add latency, cost and nondeterminism to a problem with a known answer. Nodes are wired with explicit edges for exactly that reason.

Position

The shopper picks their floor and aisle

The start node is whatever they select — no beacons, no Wi-Fi trilateration, no hardware. The data model is already shaped for QR aisle markers later, since a scanned code sets the same node.

Location model

Floor → Zone → Aisle → Rack → Shelf → Facing

Rack is a first-class level rather than a detail inside an aisle, because that is the granularity asked for. The planogram world calls this a bay; the data model uses "rack" so the vocabulary matches the conversation.

One SKU maps to several locations — its home rack plus promotional end caps — so the lookup returns a list, and the router picks the nearest member.

Routing

Precompute distances once; never search at request time

The layout is static, so all-pairs shortest paths across all three floors are computed at startup in a single call and cached. Roughly 300 nodes makes this instant, and every single-product query becomes an O(1) table lookup.

Vertical connectors are weighted edges, which is what makes the router avoid pointless floor changes. Tagging the lift as step-free and trolley-friendly gives accessibility routing almost free: filter the graph to lift-only edges and recompute.

Routing

Multi-product is sequencing, not pathfinding

The shortest paths already sit in the matrix. What is left is a travelling-salesman problem — nearest-neighbour construction, then 2-opt, over the precomputed distances. Milliseconds for a basket of any realistic size.

Because the route ends at the tills it is a closed path, not an open one, which also makes deferring chilled and frozen items to the final floor natural rather than bolted on.

Availability

Stock is treated as live and correct

Granted as an assumption, so there is no staleness handling and an exact count can be shown rather than a vague band. Worth saying plainly that this is a concession, not a property of real stock systems — shelf-level accuracy is one of the harder problems in grocery.

Gen AI

The model interprets and phrases; it never supplies a fact

Three nodes call a model and none of them is on the wire that returns a location, a distance or a stock figure. A hallucinated rack number sends a shopper to the wrong floor, so the model is architecturally unable to produce one.

Substitution candidates are filtered on structured dietary attributes before the model sees them, so it chooses among already-safe options rather than judging safety. Nothing generated asserts that a product is gluten free, nut free, vegan or halal — that claim comes from a catalogue attribute, passed through verbatim.

Stack

No database, no frontend framework

The whole dataset is a few hundred kilobytes held in memory. A database adds setup cost and demonstrates nothing; React adds a build step for a search box, a result card and an SVG polyline.

5 · Data sources

No public dataset holds a real multi-floor supermarket planogram at rack level — shelf layout is competitive information and retailers do not publish it. The store map is therefore authored, which is the right answer anyway, since no real planogram would match a brief that asks for three floors and racks.

Traps worth knowing before the first line of code

Strict structured output is model-specific on GroqCloud. Only openai/gpt-oss-20b and openai/gpt-oss-120b enforce a JSON schema strictly; the Llama models offer JSON mode only. Every schema-bound call uses a gpt-oss model, with the model ID held in configuration.

Structured output cannot stream or call tools on GroqCloud. Neither is needed here, but a tutorial that streams will fail.

Reasoning counts against max_tokens. The gpt-oss models reason before answering; too low a cap truncates the reply mid-JSON. Keep reasoning effort low and leave headroom.

Pin versions too: the checkpointer is exported as both MemorySaver and InMemorySaver depending on release, and the pause API moved from interrupt_before to interrupt().
