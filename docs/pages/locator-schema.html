Data schema · proof of concept

Product Locator Schema

The six CSV files that describe one store: columns, types, identifier scheme, referential rules and the forty-seven checks that run before the first search. This is the contract for onboarding a store.

Files six CSVs, one folder per store Demo store 314 nodes · 352 edge rows · 3 floors Validation 47 checks, V-01 to V-47

1  The store folder

One store is one folder. The folder name is the store identifier — there is no store ID threaded through every row, because running more than one store concurrently is out of scope and a repeated key is a repeated chance to disagree.

data/
  SBY-DEMO-001/          ← three-floor demo store
    store.csv
    products.csv
    stock.csv
    planogram.csv
    map_nodes.csv
    map_edges.csv
  SBY-PORT-002/          ← two-floor portability store (AC-09)
    …the same six files

1.1  Six files, four kinds of data

FileKindShapeRows
store.csvprovenancekey–value5
products.csvcatalogueone row per SKU~180
stock.csvstock positionone row per SKU~180
planogram.csvplanogramone row per placement — the join table~250
map_nodes.csvstore mapone row per walkable point~310
map_edges.csvstore mapone row per path~350

Why six files and not the four FR-25 names. FR-25 says a different store works by replacing the data files only, and the requirements count four kinds of data. A graph does not fit one table, so the map is two files — that was settled. store.csv is the sixth, and it exists because three facts are properties of the store rather than of any row: the planogram version, the stock extract time, and the statement that the data is synthetic (C-04). The alternative is repeating all three on every row of three files, where they can drift apart. FR-25's wording should read "the data files" rather than "the four data files" — the requirement is unchanged, the count was never the point.

Three cardinalities carry meaning and are enforced in §6:

  • stock.csv is total over products.csv. Every SKU has a stock row. A missing row is an authoring mistake, never a meaning — "we don't carry it" is said with ranged=false, not with absence.
  • planogram.csv is partial. A SKU with no placement is legitimate: it is not ranged here (EC-04), or it is ranged but has no recorded shelf (EC-19).
  • planogram.csv is many-to-one on both keys. One SKU may hold several placements (EC-20, the normal case) and one node holds many SKUs.

2  CSV conventions

These are not stylistic. Each one closes a failure mode that CSV introduces and JSON did not have.

2.2  The three-state boolean

This is the single most important rule in the document.

A dietary flag has three states: true, false and unknown. CSV has no null, so the encoding is explicit and the vocabulary is closed:

Cell contentMeans
trueTrue. Recorded, affirmative
falseFalse. Recorded, negative — someone checked
(empty)Unknown. Nobody checked

Nothing else is accepted. TRUE, True, T, 1, 0, yes, Y, NULL, N/A, -, n/a and a cell of spaces are all refusals (V-04), including in the two-state columns. A loader that coerces is a loader that guesses.

The trap this closes. pandas.read_csv reads an empty cell as NaN, and NaN is falsy in Python. So if product.diet_gluten_free: silently means "not gluten free" for every product nobody checked — the exact collapse NFR-03 forbids, arrived at by doing nothing wrong in particular. The loader must read these columns as strings and map the three tokens explicitly. Never dtype=bool, never fillna(False), never a truthiness test at a read site.

Which columns are three-state, and which are two. Every diet_* column is three-state — that is what the prefix is for, so the rule is one rule and not a list to remember. age_restricted, own_brand, ranged, seasonal, bidirectional, step_free, trolley and is_open are two-state and required: an empty cell is a refusal. Age restriction is a legal fact the retailer knows about every line it sells, and an edge either is step-free or it is not. Unknown is not a state those fields have, and pretending otherwise would make the three-state rule look like decoration rather than a safety property.

2.3  List-valued columns

synonyms and allergens_contains hold lists. They are pipe-delimited (|), not comma-delimited, because a comma is the field delimiter and the quoting that would be needed does not survive a round trip through a spreadsheet.

coke|cola|coca cola
  • Segments are trimmed of surrounding spaces; inner spaces are kept.
  • No empty segments, no leading or trailing | (V-05).
  • An empty cell is an empty list — except for allergens_contains, below.

allergens_contains is three-state at list level. This is §2.2's rule again, one level up, and it is easy to get wrong:

Cell contentMeans
`milk\soya`Checked. Contains milk and soya
noneChecked. Contains none of the declared allergens
(empty)Unknown. The declaration has not been recorded

The literal none is a value, not a convention — it is how the data says "somebody looked and the answer was nothing", which is a different claim from an empty cell. none may not appear alongside another allergen (V-22).

2.4  Columns that must be read as text

ColumnRisk
skuA spreadsheet reads 7123456 as a number. Any SKU with a leading zero loses it, permanently and silently
barcodeEAN-13 is 13 digits. Excel renders it as 5.449E+12 and saves it that way
node_id, edge_id, from_node, to_nodeSafe in practice (they start with a letter) but declared text for consistency

The authoring guidance is one line: format these columns as Text before typing in them, and never open a store folder in Excel without doing so. A loader cannot reliably detect the damage after the fact — 5449000000996 and 5.449E+12 are both plausible cell contents, and a lost leading zero leaves a valid-looking SKU. V-21 catches the length violation on barcode; nothing catches a mangled sku except a broken join, which is why the convention is that SKUs do not begin with a zero.

2.5  Numbers and units

QuantityTypeConvention

Coordinates are presentational and distances are authoritative. x_m/y_m exist to draw the floor plate and the route overlay (FR-20). They are never used to compute a distance — every distance comes from weight_m on the edges. The two can legitimately disagree: an aisle you cannot walk straight down is longer than the gap between its endpoints. W-03 warns when they disagree beyond a tolerance, because a large disagreement is usually a typo rather than a dogleg.

3  Identifier scheme

Every walkable point has an identifier that encodes where it is. The format is load-bearing: it makes a wrong identifier visible by eye, and it lets the UI label a location without a lookup.

RackF{level}-A{aisle:02}-R{rack:02}F1-A07-R03yes

Levels are integers, 0 upward, and are contiguous — F0, F1, F2. Aisle and rack numbers are zero-padded to two digits in the identifier and stored unpadded in their own integer columns; both are present, and V-50 checks they agree. The redundancy is deliberate: the identifier is for humans reading a diff, the columns are for the code.

The graph stops at rack level. A shelf is not somewhere you walk, so it is a column on a placement rather than a node. That keeps the map at roughly 310 rows instead of 1,200 and still lets directions name a shelf:

F1 · A07 · R03   ·   S02 · P1
└── routable ──┘     └ columns ┘
   a graph node        spoken, not walked

Three node types are new here, and they close a gap: LLD §2 had no format for a counter, a locked cabinet or a dump bin, while LLD §3.2 required location_type values of COUNTER, ASSISTED and DUMP_BIN that must route somewhere. A deli counter is not a rack — it has no shelf and no facing — so it gets its own type rather than being a rack that lies about itself. This is what makes V-46's compatibility check expressible.

4  File schemas

Legend for the Req column: Y required, non-empty · N optional, empty permitted and meaningful · 3 three-state per §2.2.

4.1  store.csv

Two columns, key and value, one row per key. The key set is closed: a missing key and an unknown key are both refusals (V-10).

keyvalueExample
store_idtext, must equal the folder nameSBY-DEMO-001
store_nametext, shown in the UISainsbury's Demo Superstore
data_provenancesynthetic — the only accepted valuesynthetic
planogram_versionISO date; bumped by a range change2026-10-01
stock_as_ofISO 8601 UTC timestamp2026-10-09T08:40:00Z

Why key–value rather than columns. This is the one file whose content is not a list of records, and a two-column shape means adding a store-level fact later never changes a header. data_provenance earns its row by making C-04's "synthetic data" statement a property of the data: the portability store cannot be onboarded without declaring it, so the banner cannot be lost by forgetting to hard-code it.

Not in this file: min_level and max_level, which are derived from map_nodes.level, and the default start node, which is the sole entrance node. Both were fields in LLD §3.4. Deriving them removes a class of disagreement between the map and the thing describing the map, and retires LLD §13 check 10.

4.3  stock.csv

One row per SKU, total over products.csv. The branch position.

ColumnTypeReqConstraint / note
skutextYPK and FK → products.sku
rangedboolYTwo-state. Carried by this branch
shelf_qtyintY≥ 0

ranged is load-bearing. ranged=false and shelf_qty=0 are different answers to a shopper — "we don't carry it at this branch" against "we carry it and it's sold out" — they take different paths through the graph, and FR-08 requires the distinction. Conflating them is EC-04.

ranged=false with shelf_qty>0 is contradictory and refused (V-31). A real feed does produce it, for a line being run out, and that is a third answer ("last few, then gone") rather than a variation on the first two. It is not modelled, so it is not permitted — a run-out state would be a new column here, not new code.

There is no encoding for "quantity unknown." EC-18's unknown-availability state is a runtime condition — the stock service unreachable in a real build — and this is a file, which is either present or not. An empty shelf_qty is a refusal rather than an unknown, so nobody can introduce a silent third state into the one column where a guess becomes a shopper walking to an empty shelf.

4.4  planogram.csv

One row per placement. The join table — sku into the catalogue, node_id into the map.

PK is the composite (sku, node_id, shelf_no, facing_from). No surrogate placement_id, because nothing references a placement — unlike an edge, which needs a name so it can be taken out of service. A SKU legitimately appears twice on the same rack at different shelves, so the composite is the natural key and (sku, node_id) alone is not unique.

Column names differ from LLD §3.2 — shelf→shelf_no, facing→ facing_from, facings→facing_count. In a JSON object facing and facings are merely similar; as adjacent CSV headers they are a transcription error waiting to happen.

4.5  map_nodes.csv

One row per walkable point.

ColumnTypeReqConstraint / note
node_idtextYPK. Format per §3, consistent with node_type
node_typeenumYrack · aisle_end · junction · core · counter · cabinet · bin · entrance · till

floor_name is denormalised on purpose. It is a property of a level and repeats on every node of that level. The alternatives were a third map file or a mixed-shape store.csv, and the map is two files by settled decision. A spreadsheet author fills the column down; V-51 refuses a store where two nodes on one level disagree. The repetition is paid for by one validation rule.

aisle is optional on a counter, a cabinet and a bin because their identifiers encode no aisle (§3) and directions still want to say one — "aisle 12, the locked cabinet on your left" is a better instruction than "the locked cabinet". It is context for the phrasing, not an address: the node_id is the address, and V-50 does not cross-check this column for these three types because there is nothing in the identifier to check it against.

shelf_count is new. Without it, shelf_no has no upper bound and "eye level" cannot be derived from a shelf number — shelf 2 of 3 is eye level, shelf 2 of 6 is not. FR-10 asks for a shelf, and the directions in FR-20 want to say it in words.

zone is a label, and closures are per-node. EC-32 speaks of a zone carrying an open flag; is_open is on the node instead. A node is the thing with a position, closing an arbitrary set of nodes is strictly more capable than closing whole zones, and it needs no zone table — so zone stays a string used for grouping and labelling, with nothing hanging off it.

4.6  map_edges.csv

One row per path between two nodes. The row is undirected or directed according to bidirectional; the loader expands it into the directed graph.

ColumnTypeReqConstraint / note
edge_idtextYPK. E{n:04}, e.g. E0137
from_nodetextYFK → map_nodes.node_id
to_nodetextYFK → map_nodes.node_id, ≠ from_node
kindenumYaisle · corridor · lift · escalator · stairs. The demo store uses no escalator — FR-14 commits to stairs and lifts — but the format accepts one, because FR-25 means another store may have them
weight_mfloatY> 0. Walking distance in metres
penalty_mfloatY≥ 0. Wait cost as its walking equivalent
bidirectionalboolYTwo-state. false = from_node → to_node only
step_freeboolYTwo-state. false for escalator and stairs (V-62)
trolleyboolYTwo-state. false for stairs (V-62)
is_openboolYTwo-state. false removes the edge (EC-30)

Effective weight is weight_m + penalty_m, and that is the only arithmetic the loader does to an edge.

Why the lift penalty is in metres. A lift ride is about 6 m of travel plus perhaps 30 seconds of waiting. Rather than mixing units, the wait is converted to its walking equivalent, so the matrix stays in one unit and Dijkstra needs no special case for vertical edges. It is also the single tuning knob for "stop bouncing between floors": raise the penalty and the router clusters harder by floor. If "optimal" is later redefined as time (A-05), convert every weight to seconds and nothing else changes.

Why edge_id exists when placement has no surrogate key. Two nodes can be joined by more than one path — the rear core carries both a lift and stairs between the same pair of core nodes — so (from_node, to_node) is not unique and the table is a multigraph. An out-of-service connector also has to be nameable: LLD §4's invalidate(disabled) needs a handle, and "the rear lift between floors 1 and 2" is E0137.

The loader must collapse parallel edges to the minimum effective weight. A sparse adjacency matrix holds one value per cell, so three rows joining the same pair become one entry — the cheapest. For the step-free matrix, filter to step_free=true first and then take the minimum, or the stairs' lower weight hides the lift that the step-free route depends on. Doing it in the wrong order produces a step-free matrix that is quietly the same as the full one, which AC-07 would catch and a reviewer might not.

Vertical edges join two core nodes at the same core position (FRONT or REAR) on different levels (V-63). Non-adjacent levels are permitted — an express lift is a real thing — but the pair must still be the same core, because a lift that arrives in a different part of the building is two connectors. bidirectional=false exists for escalators, which are genuinely one-way, and is why the graph is built directed. The demo store has none, so every row in it is bidirectional — but the matrix build must not assume that, or the first store with an escalator routes shoppers the wrong way up one.

R-1 is total in both directions and it is the only one that is: every product has exactly one stock row and every stock row has a product. A SKU in the stock file but not the catalogue is a stale extract; a SKU in the catalogue with no stock row has no answer to FR-07.

R-2 and R-3 are deliberately partial, and the gap carries meaning — products ⟶ no placement is EC-19 or EC-04, and a map_nodes row with no placement is most of the map.

7  Validation

Run once when the store folder is loaded, before the first query is served. Invalid data stops the load — NFR-07, and AC-14 requires each refusal to name the fault. A data error is not a request-time edge case; a half-loaded store is never served.

IDs are stable and gaps between blocks are intentional, so a new rule does not renumber the ones a test references.

7.9  Warnings

These load the store and log. Each describes data that is suspicious but has a defined meaning, and refusing would block a legitimate case.

IDWarningWhy not a refusal
W-01An aisle_category whose products sit on racks in more than one aisleLegitimate for a category split across an aisle boundary, but usually a typo in one row
W-02A SKU with ranged=true and shelf_qty>0 but no placementEC-19 explicitly handles it — availability is shown and the location reads as unknown
W-03An aisle or corridor edge whose weight_m differs from the straight-line distance between its endpoints' coordinates by more than 50%Legitimate for a dogleg; a large disagreement is usually a mistyped weight (§2.5)
W-04A node of type rack with no placements on itAn empty rack is real; a floor of them means the planogram was not finished
W-05A diet_* column empty for more than half the catalogueHonest unknown, but it makes dietary filtering useless, and silently so

W-02 and V-32 are the same shape of problem with different answers, and the difference is the point. A missing stock row has no meaning, so it is refused. A missing placement has a defined meaning that the system already handles, so it warns. A validation tier that refuses everything suspicious cannot be lived with, and one that warns about everything is not validation.

Edge rows: 180 rack-to-rack (5 per aisle × 36) + 72 rack-to-aisle-end + 66 corridor segments between adjacent aisle ends + 12 junction links + 8 vertical (2 lifts × 2 spans, 2 stairs × 2 spans — no escalators, FR-14) + 1 entrance + 6 till + 7 counter, cabinet and bin links = 352 rows. Every row in the demo store is bidirectional, so expanding each into two arcs gives 704 directed arcs.

This corrects the "~900 edges" figure carried in lld.md §4, architecture.md §4 and the HLD's review answers. Those numbers predate the rack-level layout being pinned down and were never derived; ~700 is what the arithmetic above gives. The node figure of ~300 stands — 314 against an estimated 300. Neither changes any conclusion: Dijkstra from every node is ~1M operations either way, and the matrices are about 2 MB for both pairs.

The aisle, rack and till counts are authoring choices, not derived facts. Changing them changes only map_nodes.csv, map_edges.csv and the node_id values in planogram.csv — which is precisely what FR-25 and AC-09 test.
