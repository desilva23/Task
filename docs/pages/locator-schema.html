Data schema · proof of concept

Product Locator Schema

The six CSV files that describe one store: columns, types, identifier scheme, referential rules and the forty-seven checks that run before the first search. This is the contract for onboarding a store.

Files six CSVs, one folder per store Demo store 314 nodes · 352 edge rows · 3 floors Validation 43 refusals and 5 warnings, checked at load

1  The store folder

One store is one folder, and the folder name is the store identifier — no store ID is repeated on every row.

data/
  SBY-DEMO-001/          ← three-floor demo store
    store.csv
    products.csv
    stock.csv
    planogram.csv
    map_nodes.csv
    map_edges.csv
  SBY-PORT-002/          ← two-floor portability store (AC-09)
    …the same six files

1.1  Six files, four kinds of data

FileKindShapeRows
store.csvprovenancekey–value5
products.csvcatalogueone row per SKU~180
stock.csvstock positionone row per SKU~180
planogram.csvplanogramone row per placement — the join table~250
map_nodes.csvstore mapone row per walkable point~310
map_edges.csvstore mapone row per path~350

The map is two files because a graph does not fit one table. store.csv holds the three facts that belong to the store rather than to any row: the planogram version, the stock extract time, and the statement that the data is synthetic (C-04).

1.2  How they join

planogram.csv is the join table: sku into the catalogue, node_id into the map. Three cardinalities carry meaning, and §6 enforces them:

  • stock.csv is total over products.csv. Every SKU has a stock row. "We don't carry it" is said with ranged=false, never with a missing row.
  • planogram.csv is partial. A SKU with no placement is legitimate — not ranged here (EC-04), or ranged with no recorded shelf (EC-19).
  • planogram.csv is many-to-one both ways. One SKU may hold several placements (EC-20, the normal case) and one node holds many SKUs.

2  CSV conventions

Each one closes a failure mode CSV introduces.

2.1  File format

RuleValueWhy

QuotingRFC 4180 — double quotes, doubled to escapeProduct names contain commas and apostrophes

2.2  The three-state boolean

The single most important rule here. A dietary flag has three states, and CSV has no null, so the vocabulary is explicit and closed:

Cell contentMeans
trueTrue. Recorded, affirmative
falseFalse. Recorded, negative — someone checked
(empty)Unknown. Nobody checked

TRUE, T, 1, 0, yes, NULL, N/A, - and a cell of spaces are all refusals (V-04). A loader that coerces is a loader that guesses.

The trap. pandas.read_csv reads an empty cell as NaN, which is falsy, so if product.diet_gluten_free: silently means "not gluten free" for every product nobody checked — the collapse NFR-03 forbids. Read these columns as strings and map the three tokens explicitly. Never dtype=bool, never fillna(False).

**Every diet_* column is three-state. age_restricted, own_brand, ranged, seasonal, bidirectional, step_free, trolley and is_open are two-state and required** — an empty cell is a refusal. Those fields have no unknown state.

2.3  List-valued columns

synonyms and allergens_contains are pipe-delimited (|) — a comma is the field delimiter, and the quoting needed to escape it does not survive a round trip through a spreadsheet.

coke|cola|coca cola
  • Segments are trimmed of surrounding spaces; inner spaces are kept.
  • No empty segments, no leading or trailing | (V-05).
  • An empty cell is an empty list — except for allergens_contains, below.

allergens_contains is three-state at list level — §2.2's rule one level up:

Cell contentMeans
`milk\soya`Checked. Contains milk and soya
noneChecked. Contains none of the declared allergens
(empty)Unknown. The declaration has not been recorded

none is a value, not a convention: it says somebody looked and found nothing, which is a different claim from an empty cell. It may not appear alongside another allergen (V-22).

2.4  Columns that must be read as text

ColumnRisk
skuA spreadsheet reads 7123456 as a number. Any SKU with a leading zero loses it, permanently and silently
barcodeEAN-13 is 13 digits. Excel renders it as 5.449E+12 and saves it that way
node_id, edge_id, from_node, to_nodeSafe in practice (they start with a letter) but declared text for consistency

Format these columns as Text before typing in them. A loader cannot detect the damage afterwards — a lost leading zero leaves a valid-looking SKU. Hence the convention that SKUs never begin with a zero.

2.5  Numbers and units

QuantityTypeConvention
Distance (weight_m, penalty_m)float, metresOne decimal place. Metres throughout — the only unit in the data
Coordinates (x_m, y_m)float, metresOne decimal. Per-store origin, shared across floors so the cores line up vertically
Counts (shelf_qty, shelf_no, facing_from, facing_count, shelf_count, aisle, rack)int ≥ 0No thousands separators
price_gbpdecimal, 2 dpDisplay only. Never summed, never compared. Pounds, no symbol
popularityfloat, 0.0–1.02 dp. A ranking tiebreak, nothing else
Timestamp (stock_as_of)ISO 8601, UTC, Z suffix2026-10-09T08:40:00Z

Coordinates are presentational; distances are authoritative. x_m/y_m draw the floor plate (FR-20) and are never used to compute a distance — that comes from weight_m. They may legitimately disagree, so W-03 warns rather than refuses.

3  Identifier scheme

Every walkable point has an identifier that encodes where it is, so a wrong one is visible by eye.

RackF{level}-A{aisle:02}-R{rack:02}F1-A07-R03yes

Service counterF{level}-CTR-{n:02}F0-CTR-01yes
Assisted cabinetF{level}-CAB-{n:02}F1-CAB-01yes
Dump binF{level}-BIN-{n:02}F0-BIN-01yes

Levels are integers from 0 and contiguous. Aisle and rack numbers appear zero-padded in the identifier and unpadded in their own columns; V-50 checks they agree. The identifier is for humans reading a diff, the columns are for the code.

The graph stops at rack level. A shelf is not somewhere you walk, so it is a column on a placement rather than a node. That keeps the map at roughly 310 rows instead of 1,200 and still lets directions name a shelf:

F1 · A07 · R03   ·   S02 · P1
└── routable ──┘     └ columns ┘
   a graph node        spoken, not walked

counter, cabinet and bin are new here. The LLD could label a product as being at a counter but had no node format to route to — and a deli counter is not a rack, because it has no shelf and no facing.

4  File schemas

Legend for the Req column: Y required, non-empty · N optional, empty permitted and meaningful · 3 three-state per §2.2.

4.1  store.csv

Two columns, key and value. The key set is closed — a missing or unknown key is a refusal (V-10).

4.3  stock.csv

One row per SKU, total over products.csv. The branch position.

ColumnTypeReqConstraint / note
skutextYPK and FK → products.sku
rangedboolYTwo-state. Carried by this branch
shelf_qtyintY≥ 0

ranged is load-bearing. ranged=false and shelf_qty=0 are different answers to a shopper — "we don't carry it here" against "we carry it and it's sold out" — and FR-08 requires the distinction. ranged=false with shelf_qty>0 is contradictory and refused (V-31).

There is no "quantity unknown". EC-18 is a runtime condition, not a data state; an empty shelf_qty is a refusal. This is the one column where a guess sends a shopper to an empty shelf.

4.5  map_nodes.csv

One row per walkable point.

ColumnTypeReqConstraint / note
node_idtextYPK. Format per §3, consistent with node_type
node_typeenumYrack · aisle_end · junction · core · counter · cabinet · bin · entrance · till
levelintY≥ 0, contiguous across the store
floor_nametextNRepeated per level; must agree (V-51)
aisleintNRequired for rack and aisle_end; optional on counter, cabinet and bin; empty otherwise
rackintNRequired for rack, else empty

Three columns need a word.

  • floor_name repeats on every node of a level. An author fills it down; V-51 refuses a store where two nodes on one level disagree.
  • shelf_count bounds shelf_no and lets "eye level" be derived — shelf 2 of 3 is eye level, shelf 2 of 6 is not.
  • zone is a label with nothing hanging off it. Closures are per-node via is_open, which is more capable than closing whole zones and needs no zone table.

4.6  map_edges.csv

One row per path between two nodes. The row is undirected or directed according to bidirectional; the loader expands it into the directed graph.

ColumnTypeReqConstraint / note
edge_idtextYPK. E{n:04}, e.g. E0137
from_nodetextYFK → map_nodes.node_id
to_nodetextYFK → map_nodes.node_id, ≠ from_node
kindenumYaisle · corridor · lift · escalator · stairs. The demo store uses no escalator — FR-14 commits to stairs and lifts — but the format accepts one, because FR-25 means another store may have them
weight_mfloatY> 0. Walking distance in metres
penalty_mfloatY≥ 0. Wait cost as its walking equivalent
bidirectionalboolYTwo-state. false = from_node → to_node only
step_freeboolYTwo-state. false for escalator and stairs (V-62)
trolleyboolYTwo-state. false for stairs (V-62)
is_openboolYTwo-state. false removes the edge (EC-30)

Four rules the loader must follow.

  • Effective weight is weight_m + penalty_m. The only arithmetic done to an edge.
  • The lift penalty is in metres, not seconds: a 30-second wait becomes its walking equivalent, so the matrix stays in one unit. It is also the tuning knob for floor-bouncing — raise it and the router clusters harder by floor.
  • Parallel edges collapse to the minimum effective weight. The rear core carries both a lift and stairs between the same pair of nodes, so (from_node, to_node) is not unique — which is why edge_id exists. **For the step-free matrix, filter to step_free=true first and then take the minimum**, or the stairs' lower weight hides the lift. The wrong order gives a step-free matrix quietly identical to the full one.
  • **A vertical edge joins two core nodes at the same core position on different levels** (V-63). Non-adjacent levels are allowed — an express lift is real — but a connector arriving at a different core is two connectors.

6  Referential integrity

#RelationshipCardinalityTotal?Violation
R-1stock.sku → products.sku1:1Yes, both waysRefuse (V-30, V-32)
R-2planogram.sku → products.skuN:1NoRefuse on orphan (V-40)
R-3planogram.node_id → map_nodes.node_idN:1NoRefuse on orphan (V-41)
R-4map_edges.from_node → map_nodes.node_idN:1NoRefuse (V-60)
R-5map_edges.to_node → map_nodes.node_idN:1NoRefuse (V-60)
R-6store.store_id → folder name1:1YesRefuse (V-11)

R-1 is total in both directions and it is the only one that is: every product has exactly one stock row and every stock row has a product. A SKU in the stock file but not the catalogue is a stale extract; a SKU in the catalogue with no stock row has no answer to FR-07.

R-2 and R-3 are deliberately partial, and the gap carries meaning — products ⟶ no placement is EC-19 or EC-04, and a map_nodes row with no placement is most of the map.

7  Validation

Run once when the store folder is loaded, before the first query is served. Invalid data stops the load — NFR-07, and AC-14 requires each refusal to name the fault. A data error is not a request-time edge case; a half-loaded store is never served.

IDs are stable and gaps between blocks are intentional, so a new rule does not renumber the ones a test references.

7.9  Warnings

These load the store and log. Each is suspicious but has a defined meaning, so refusing would block a legitimate case.

IDWarningWhy not a refusal
W-01An aisle_category whose products sit on racks in more than one aisleLegitimate for a category split across an aisle boundary, but usually a typo in one row

The line between the tiers: a missing stock row has no meaning, so it is refused. A missing placement has a meaning the system already handles, so it warns.

8  Sizing

The catalogue and the stock position do not grow with floor count — the same ~180 products sit somewhere, so only the map changes shape. That is what makes a three-floor demo nearly free.

Edge rows: 180 rack-to-rack (5 per aisle × 36) + 72 rack-to-aisle-end + 66 corridor segments between adjacent aisle ends + 12 junction links + 8 vertical (2 lifts × 2 spans, 2 stairs × 2 spans — no escalators, FR-14) + 1 entrance + 6 till + 7 counter, cabinet and bin links = 352 rows. Every row in the demo store is bidirectional, so expanding each into two arcs gives 704 directed arcs.

The portability store is shaped differently on purpose, not just shorter: two floors, 15 aisles (8 + 7) of 5 racks rather than 6, several categories sharing each aisle so a rack holds several products on different shelves, four tills, and both locked cabinets on floor 1. Its catalogue and stock files are the demo store's, unchanged — only the map and the planogram move.

The aisle, rack and till counts are authoring choices, not derived facts. Changing them touches only the two map files and the node_id values in planogram.csv — which is what FR-25 and AC-09 test.
