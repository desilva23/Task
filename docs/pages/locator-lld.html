Two rules the layout enforces. graph/nodes/ may import from services/, never the reverse, and services/* never imports langchain or langgraph — which keeps the deterministic core testable without a graph runtime and without a model, and is what makes the fallbacks in §6 honest rather than aspirational. And nothing outside api/ imports fastapi, starlette or uvicorn: the API is the only module that knows it is a web service, so the graph and the services run the same under a test, a script or the function.

The page is a separate program in TypeScript. It holds no fact: every statement, direction and floor plate it shows arrived from the API already verified, and it renders all of it as text except the plates (§11).

Path reconstruction:

def path(self, u, v, step_free=False):
    P = self.P_step if step_free else self.P_full
    i, j = self.g.index[u], self.g.index[v]
    if i == j:
        return [u]                                  # EC-25, zero-length
    if P[i, j] == NO_PATH:                          # NO_PATH = -9999
        raise UnreachableNodeError(u, v)            # EC-29
    out, k = [v], j
    while k != i:
        k = int(P[i, k])
        out.append(self.g.rev[k])
    return list(reversed(out))

class JourneyState(TypedDict):
    # request, written once
    store_id:   str
    action:     Literal["search", "scan", "plan"]
    raw_query:  str
    barcode:    str                      # scan only — digits as decoded or typed (FR-03)
    mode:       Literal["auto", "single", "multi"]
    start_node: str
    step_free:  bool

    # classification
    shape:  Literal["too_short", "digits", "batch", "nl", "term", "barcode", "bad_barcode"]
    terms:  list[SearchTerm]                 # {text, qty}
    parsed: ParsedQuery | None

    # resolution
    candidates:  dict[str, list[Product]]    # term → ranked candidates
    resolved:    dict[str, str]              # term → chosen SKU
    unresolved:  list[str]                   # matched nothing — EC-08
    not_ranged:  list[str]                   # real but not stocked here — EC-04

    # availability and location
    availability: dict[str, StockPosition]
    locations:    dict[str, list[Placement]]
    substitutes:  dict[str, list[Product]]

    # basket — the input to routing
    basket: Annotated[list[BasketItem], merge_basket]

    # output
    route:      Route | None
    directions: list[str]

    # control
    clarify_rounds: int                                 # capped at 2 — EC-35
    degraded:  Annotated[list[str], operator.add]       # nodes that fell back
    errors:    Annotated[list[JourneyError], operator.add]
    verified:  bool                                     # set by verify — EC-47
    mismatches: Annotated[list[Mismatch], operator.add] # claim, expected, found

Three fields earn their place:

  • basket carries a custom reducer rather than operator.add, because two concurrent adds of the same SKU must merge quantities instead of producing a duplicate row (EC-07).
  • degraded records every node that used its fallback, and the response carries it — so a demo that quietly ran without a model is visible rather than mysterious.
  • clarify_rounds is what makes the cycle terminate.
  • verified is false until verify has passed the composed answer. The page renders nothing while it is false, which is how NFR-02 becomes a property of the state machine rather than a discipline.

Every run that makes a claim ends through verify — a search that returns results without a route included. Its availability and location statements are claims too, and NFR-02 covers every claim, not only directions.

A route-planning run enters at resolve_locations. plan_route starts the graph there with the basket, so routability is re-checked from current stock on every run (EC-17) and the basket is replaced, not merged — an item the shopper removed on the page cannot reappear.

State holds identifiers and plain values only — SKUs, node IDs, numbers and text, never product or placement objects. Nodes read facts from the services each time, so a checkpoint is safe to serialise and cannot carry a stale fact.

One adapter stands between the nodes and any model. ModelClient.complete returns the model's raw output and the node validates it against the schema itself (extra="forbid"), so a response carrying a product name or a SKU is rejected by our code whatever the provider does (AC-18). A fake client drives every test; GroqCloud implements the same adapter in Phase 6.

describe_route → verify → END is a plain edge, not a conditional one, and verify has no outgoing branch that skips it. That is deliberate: a conditional edge is a decision someone can get wrong, and there must be no path from a composed answer to the page that does not pass the gate.

8  Search internals

8.1  Index construction

def searchable_text(p: Product) -> str:
    return " ".join([p.name, p.brand, p.size, p.aisle_category, *p.synonyms])

def normalise(text: str) -> list[str]:
    t = unicodedata.normalize("NFKD", text).encode("ascii", "ignore").decode()
    t = t.lower()
    t = re.sub(r"[^a-z0-9%.]+", " ", t)   # keep digits, % and . for "500ml", "1.5l"
    return [tok for tok in t.split() if tok not in STOPWORDS]

index = BM25Okapi([normalise(searchable_text(p)) for p in products], k1=1.2, b=0.5)

b=0.5 rather than the usual 0.75: b controls how hard a long document is penalised, and product names are all short, so the standard value over-penalises the ones that happen to carry synonyms. Both constants belong on the eval set, not in a reviewer's opinion.

Named products first. The category and the size are in the index so that a query naming nothing still finds something, but they are weak evidence. After BM25, the candidates are narrowed to the best non-empty tier:

  1. products whose name, brand or synonyms contain every query word;
  2. products whose name, brand or synonyms contain some query word;
  3. everything BM25 found.

Found live on 2026-10-14: "eggs" offered two yogurts, because their category is "Eggs & Yogurt"; "tea" offered coffee, "kitchen roll" facial tissues, "ice cream" antiseptic cream, "coca cola" Pepsi. An audit over every name, word and synonym in the catalogue found 94 of 569 queries offering something not named; after the tiers, the only ones left are brand matches (Diet Coke for "coca"). The audit is a unit test, so a new product cannot bring the problem back.

A partial name is a suggestion, not an answer. A term resolves only when the top candidate is named by at least one of the search's words and accounts for all of them — its name, brand, synonyms or size, a misspelling within FUZZY_THRESHOLD included (names_all). Otherwise the term is unresolved and the candidates become suggestions (EC-03). Found live: "face wash" answered with Shower Gel, whose synonym "body wash" shares one word. Sentences are exempt — they are never auto-resolved anyway — and so is a search the model has already narrowed with a filter.

8.2  Query classification

SPLIT  = re.compile(r"[,;\n]|\s+and\s+|\s*\+\s*", re.I)
DIGITS = re.compile(r"^\d{8,13}$")
QTY    = re.compile(r"^(\d+)\s*(?:x|×)?\s+(.+)$", re.I)
NL_CUE = re.compile(r"\b(for|with|need|want|make|making|something|what|how|recipe)\b", re.I)

def classify(raw: str) -> tuple[str, list[SearchTerm]]:
    q = tidy(raw)          # collapse spaces per line — keep newlines, they separate items
    if len(q) < MIN_QUERY_CHARS:  return "too_short", []
    if DIGITS.match(q):           return "digits", []          # not a product request
    parts = [p.strip() for p in SPLIT.split(q) if p.strip()]
    if len(parts) > 1:
        return "batch", [parse_qty(p) for p in parts[:MAX_BATCH_TERMS]]   # EC-06
    if len(q.split()) > NL_WORD_THRESHOLD and NL_CUE.search(q):
        return "nl", []
    return "term", [parse_qty(q)]

Order matters, and one rule needs a guard. " and " splits before the natural-language test, so "milk and bread" is a batch of two rather than a sentence. Split blindly, a product with "and" in its name breaks: "salt and vinegar crisps" becomes "salt" and "vinegar crisps" — and both resolve, to table salt and the crisps, so a retry-on-failure never fires. The guard runs before the split: when the query divides only on "and", it stays one term if a single product's name contains every one of its words. "Salt & Vinegar Crisps" and "Sweet & Sour Sauce" stay whole; "milk and bread" still splits, because no product is named after both.

A list without separators is cut by the catalogue. Speech has no commas, so after classify(), each term of two to MAX_SEGMENT_WORDS (8) words that no single product is named by (names_one — names_all asked of every product) is cut into the longest runs from the left that each name one: "milk bread chicken" → milk · bread · chicken; "semi skimmed milk bread" → semi skimmed milk · bread. A word that names nothing stops the cut and the term stays whole (EC-69); a quoted term is never cut — the page's "search it as one item". The cuts travel in state as split and reach the page. A word that names a catalogue product is never read as a misspelling of another (naming_words): "bread" is not a typo of "Own Brand".

Equally named products ask. After the margin test (§8.4), when two or more candidates are named by every word (names_all), the term resolves only if exactly one product is called that — its name, a synonym, or name and size (called); otherwise it is ambiguous (EC-70).

A scan does not pass through classify(). classify_query sees action == "scan" and checks the digits with barcode.normalise instead: a valid code becomes shape barcode with the 13-digit code as its one term, and anything else becomes bad_barcode with a message (EC-52). Digits typed into the search box still take the digits branch — the search box finds names.

8.2a  Fuzzy retry and categories

When the best BM25 score is below FUZZY_TRIGGER_SCORE, search retries once:

  1. Correct each query word to the nearest word in the catalogue's own vocabulary (rapidfuzz ratio ≥ FUZZY_THRESHOLD) and rerun BM25 — "paracetomol" becomes "paracetamol", and ranking still explains itself.
  2. If that finds nothing, match the query against whole product names with WRatio ≥ FUZZY_THRESHOLD — which catches run-together words such as "cocacola".

A term equal to a department or category name that no product is named after ("dairy", "frozen") returns the category rather than an arbitrary SKU (EC-09). "Bread" and "milk" are product names too, so they search as products and come back ambiguous (EC-05).

A sentence-shaped query searched by keywords — the fallback when the model is unavailable (EC-37) — is never marked resolved. Keyword-matching a sentence is a guess, so its best matches are offered as a choice instead.

8.3  Ranking

def rank(cands: list[Scored], term: str, stock: dict) -> list[Scored]:
    return sorted(cands, key=lambda c: (
        not stock[c.sku].ranged,          # ranged first — a hard gate
        stock[c.sku].shelf_qty == 0,      # in stock before out of stock
        not variant_match(c.product, term),
        not c.near_best,                  # within the §8.4 margin of the best text score
        -c.product.popularity,
        -c.bm25,                          # a closer text match only breaks popularity ties
        not c.product.own_brand,
    ))

Near-equal text is equal text. A raw BM25 score separates "Follow On Milk" from "Semi Skimmed Milk" by a few hundredths, from nothing but the length of their descriptions, and as a ranking rule above popularity it put infant formula first for "milk". Text matches within AMBIGUITY_MARGIN of the best — the same margin §8.4 uses to call results near-equal — rank as equal, and popularity decides between them.

Each rule has a name — carried here, in stock, size asked for, text match, popularity, closer text match, own brand — and explain reports, for every result after the first, the first rule that separates it from the one above (NFR-09, AC-26).

A lexicographic tuple sort, not a weighted sum. Weighted sums need tuning and cannot be explained — "why did this rank third" has no short answer. A tuple sort is a precedence list a buyer can read, and it cannot be accidentally mis-tuned into putting an unstocked product first.

8.4  Ambiguity test

def needs_clarification(cands: list[Scored]) -> bool:
    if len(cands) < AMBIGUITY_MIN_HITS: return False
    top, second = cands[0].bm25, cands[1].bm25
    if top <= 0:                        return False
    return (top - second) / top < AMBIGUITY_MARGIN     # 0.15

A relative margin, because BM25 scores are unnormalised and vary with query length — an absolute threshold would fire inconsistently between a one-word and a three-word query.

The test runs on text-match order, not the precedence ranking. Which product the shopper named is a question of text alone. Ranked by precedence, a search for "Diet Coke" — sold out — would put Coca-Cola Zero first and silently answer with it, hiding both the sold-out state and where Diet Coke usually is (EC-13); "Pepsi Max" would quietly become a Coke (EC-04). So the clear text winner is the answer even when sold out or not carried, reported as such with alternatives, and the precedence ranking orders the options and alternatives (FR-06, AC-19).

8.5  Barcode lookup

def normalise(digits: str) -> str | None:
    d = "".join(digits.split())
    if not d.isdigit() or len(d) not in (8, 12, 13): return None
    if not check_digit_ok(d):                        return None      # EC-52
    return "0" + d if len(d) == 12 else d            # UPC-A is EAN-13 with a leading 0

def check_digit_ok(d: str) -> bool:                  # GS1: weights 3,1,3,… from the right
    body = map(int, reversed(d[:-1]))
    total = sum(n * (3 if i % 2 == 0 else 1) for i, n in enumerate(body))
    return (10 - total % 10) % 10 == int(d[-1])

Decoding is on the phone. lib/scan.ts draws a camera frame to a canvas every 250 ms (at most 1280 px on the long side) and reads it with zxing-wasm — zxing-cpp compiled to WebAssembly, the WASM file served from our own origin — for EAN13, EAN8 and UPCA only (EC-51). One distinct code stops the camera and is sent to /api/scan (EC-54); two or more are never chosen between (EC-53); after six seconds with nothing read the page says what to try (EC-49). The server trusts none of it: the digits are checked by normalise again.

Catalogue.by_barcode is a dictionary built once from products.csv; V-21 guarantees each code is valid and unique, so a code finds one product or none.

The guardrail is code, not prose. Two mechanisms, both enforced rather than requested. The schema has no field for a product name, so query understanding cannot invent one. And a substitute SKU that was not in the candidate list the service built is rejected outright — the model picks among safe options, it does not nominate them.

The understand schema is narrowed to the store. parsed_query_for(store) replaces department, aisle_category and exclude_allergens with enums of that store's own names before the schema is sent. Found live: gpt-oss read "something for a headache" well but answered with the department "pharmacy" and the category "over the counter", which matched nothing. Groq's strict decoding and our validation both reject a name the store does not have; both fields accept any real department or category name, and the node files each into the field it belongs to, because a shopper's words do not say which it is. When the item phrase finds nothing but the model named a real category, that category's products are offered as a choice.

dietary_compatible treats a null flag as incompatible when the original product required it. An unknown value never satisfies a dietary requirement.

The verify pass

The two mechanisms above stop the model inventing a fact. verify catches everything downstream of that — a stale cached figure, a mis-joined placement, a template that formatted the wrong leg. Five checks, all against state the services produced:

def verify(s: JourneyState) -> list[Mismatch]:
    m = []
    # 1 every SKU named in the answer was resolved by the search
    # 2 floor, aisle, rack and shelf equal the Placement for that SKU
    # 3 availability wording equals the StockPosition; an unavailable
    #   item has no stop in the route
    # 4 each leg distance and the total equal the plan within ROUND_TOLERANCE_M,
    #   and the floor-change count matches the connectors in the node path
    # 5 every aisle or landmark named in a step appears in the plan's node path
    return m

A non-empty list discards the composed text. The template is rendered from the same service results, verified is set on that, and the mismatch is recorded — never patched in place. Patching would hide the bug that produced it.

10  Routing internals

Single

def route_single(start, placements, step_free):
    target = min(placements, key=lambda p: engine.distance(start, p.node_id, step_free))
    nodes  = engine.path(start, target.node_id, step_free)
    return Route(nodes=nodes,
                 distance_m=engine.distance(start, target.node_id, step_free),
                 floors=floors_touched(nodes),
                 placement=target)

When a SKU has several placements (EC-20) the nearest wins — which is why distance being O(1) matters: evaluating four candidate locations is four array reads.

Multi — floor-clustered, open path per floor, closed at the tills

def route_multi(start, stops, step_free):
    order  = sorted({s.level for s in stops}, reverse=True)   # highest floor first
    seq, cursor = [], start
    for level in order:
        entry = nearest_core(cursor, level, step_free)        # arrive at the cheaper core
        here  = [s for s in stops if s.level == level]
        ambient, chilled = partition(here, lambda s: s.location_type != "CHILLER")
        floor = nn_then_2opt(entry, ambient, step_free)
        floor += nn_then_2opt(last(floor, entry), chilled, step_free)   # EC-33
        seq += floor
        cursor = seq[-1].node_id
    till = nearest_till(cursor, step_free)                    # FR-18
    nodes = stitch(start, seq, till)                          # shortest path between neighbours
    return MultiRoute(nodes=nodes, stops=seq, till=till, ...)

Chilled stops come last within their own floor's pass, not after every floor. Appending them after all floors would send a shopper back upstairs whenever a chiller sat above the ground floor, breaking FR-17's one pass per floor. In the demo store every chiller is on floor 0 — the final pass — so chilled items are still the last things picked before the tills.

A SKU held in several places takes the placement on a floor the basket already visits, nearest the start, so a second placement never adds a floor.

nn_then_2opt — open path, fixed start

def nn_then_2opt(entry, stops, step_free):
    seq, pool, cur = [], list(stops), entry
    while pool:                                        # nearest neighbour
        nxt = min(pool, key=lambda p: engine.distance(cur, p.node_id, step_free))
        seq.append(nxt); pool.remove(nxt); cur = nxt.node_id

    improved = True
    while improved:                                    # 2-opt, OPEN variant
        improved = False
        for i in range(len(seq) - 1):
            for j in range(i + 2, len(seq)):
                if delta(seq, i, j, entry) < -EPSILON: # no wrap-around term
                    seq[i+1:j+1] = reversed(seq[i+1:j+1])
                    improved = True
    return seq

Open-path 2-opt, not the textbook version. Standard 2-opt optimises a closed tour and its gain calculation includes the edge back to the origin. Each floor leg here is an open path with a fixed start and a free end, so the wrap-around term must be dropped from delta. Using the closed-tour formula produces routes that look subtly wrong — usually a last stop that doubles back — and it is an easy mistake to ship.

11  The page and the API

The page is a Next.js static export; the agent is one Python function. Between them, four calls (C-03):

CallBodyDoes
GET /api/store—Floors and the spots on each, for the position picker (FR-15); every product sold here as {sku, label, terms, in_stock, popularity} for suggestions (FR-28)
POST /api/searchquery, answers[], start, step_freeJourney.answer — the search, resumed with each round's answer (FR-05)
POST /api/scancode, start, step_freeJourney.run_scan — one exact product (FR-03)
POST /api/routeskus[], start, step_freeJourney.plan_route — the basket, routed (FR-16, FR-23)

Each returns the same shape, built by present.view.page_view from a verified state: pending (the questions, if the run paused), notice (why a run made no claim), available / unavailable rows, notes, addable and offer_add (the basket gate, FR-22), route (directions, exclusions, the floor plates as SVG) and degraded.

def _journey_run(request, response, run):
    model = make_model(budget=MODEL_CALLS_PER_SESSION - used(request))   # cookie count
    journey, thread = Journey(services(), model), f"req-{uuid4().hex}"   # ~4 ms to build
    try:
        outcome = run(journey, thread)
        return page_view(services(), outcome.state, outcome.pending)
    finally:
        journey.forget(thread)                      # nothing outlives its request (EC-34)
        set_cookie(BUDGET_COOKIE, used + model.calls)

Stateless, so it scales to zero and to many. services() is built once per function instance and reused; a journey is built per request, around that visitor's model client, and its thread is deleted before the response is sent. A clarification is answered by sending the search back with the answers — Journey.answer re-runs it and resumes it round by round; clarify accepts only an option it offered, so a stale answer is simply asked again (EC-05). The page holds the position, the basket and the answers so far, the last two in the tab's session storage (EC-41).

The floor plates are the only markup the page inserts. The SVG is drawn by our code from validated map data and carries no free text. Everything else — statements, questions, notes, directions, which can hold the shopper's or the model's words — is rendered by React as text, so nothing typed can become a link, an image or a script (AC-13).

Voice is typing. components/Voice.tsx draws its button only once mounted and only if recogniserClass() finds SpeechRecognition or webkitSpeechRecognition (EC-62). A tap builds one recogniser — lang = "en-GB", interimResults = true, continuous = false — and transcript() joins every result so far into the search box as it arrives. On end the last words heard, final or not (some recognisers end without marking them), go to POST /api/search exactly as a typed query, cut at MAX_QUERY_CHARS. failure(code) maps the recogniser's error: no-speech → not heard (EC-63); not-allowed, service-not-allowed, audio-capture → microphone unavailable (EC-61); anything else → voice not working; aborted (the page closing) → nothing. An end with no words and no error is not heard too. No API call, no server code and no model call was added.

Suggestions are matched on the phone. present.view.suggestions lists every ranged product with its label (name size, which searches straight to it — tested for every product), its terms (name, brand, each synonym), whether it is on the shelf, and its popularity. lib/suggest.ts takes the item being typed — the text after the last , ; newline + or and , the server's own separators — and keeps products where every typed word starts some word of the label or terms. Order: a label or term that starts with the typed phrase, then labels naming every typed word, then in stock, then popularity; at most six, from two characters. Choosing one replaces that item with the label and searches.

One screen. html and body are overflow: hidden and the app is a 100dvh grid — header, pane, tab bar. Panes are flex columns whose growing part has min-height: 0, so a long result list or basket scrolls inside itself; the floor plate keeps its width in a frame that scrolls, centred on the step's rack ([data-node="F1-A03-R01"], read from the step's "floor, aisle, rack"), else the floor's first pick. The directions are stepped through, each step showing the floor it names; the full list stays in the page, visually hidden, for a screen reader (NFR-10).

Failures are an apology. An unhandled error returns 500 with one sentence and is logged; a malformed request returns 422 without echoing it; the schema and docs pages are off. The page shows its own apology for either.

Local runs. npm run build then LOCATOR_STATIC=out uv run uvicorn api.index:app serves page and API from one process — what the browser tests do. npm run dev with the API on port 8000 proxies /api/* to it.

emails turns the alerts into at most two emails — low, then out — each listing product, SKU, units left and every place it is kept. notify.run loads the store, reads the previous stock.csv with git show <before>:<store>/stock.csv, swaps it into a temporary copy of the folder so the same validator loads it, and sends through AgentMail with the idempotency key <store>-<commit>-<mode>-<kind>. Settings (AGENTMAIL_API_KEY, AGENTMAIL_INBOX_ID, STORE_MANAGER_EMAIL) come from the environment; with any missing the job exits 2 without sending, and --dry-run prints instead. The agentmail SDK is in its own dependency group (alerts), imported only for a real send, so neither the site's function nor the tests carry it. .github/workflows/stock-alerts.yml runs the job on pushes to main that change the live store's stock, and by hand with current — or with sale, a demonstration: --sell "Whole Milk=3, Bananas=0" sets those shelf quantities in a temporary copy of the store and compares it with the store as it is, so the emails are exactly what a real update would send while nothing is committed. Its idempotency key uses the run id in place of the commit, so each demo run sends and a re-run of the same one does not.

13  Startup validation

The rules live in schema.md §7 — forty-three refusals numbered V-01 to V-74 with gaps between blocks, and five warnings, W-01 to W-05. They supersede the eleven checks this section used to list. They are schema territory: what makes a store folder well formed is a property of the format, not of this application. What belongs here is when they run, in what order, and what happens when one fails.

validation.py runs them when the API function first builds its services, which means they run once per instance, before its first search, and a failure raises rather than returning a half-loaded store.

PhaseChecksWhy this order
1 · ParseColumn presence, types, encodingsNothing else can run against a file that will not parse
2 · Within-fileUniqueness, ranges, enum membershipCheap, and catches most hand-authoring errors
3 · ReferentialPlacement → SKU, placement → map node, stock → SKUNeeds every file loaded, so it cannot come earlier
4 · GraphConnectivity, positive weights, every floor reachable, lift-only subgraph connectedNeeds the graph built, which needs phase 3 to have passed
5 · Store shapeAt least one checkout node, levels agree with the mapLast, because it is the only phase that encodes a requirement rather than a data rule

Phase 4 is the one worth naming in a review: the lift-only subgraph is checked for connectivity separately, because a store can be perfectly walkable and still have no step-free path between two floors. FR-19 would then be unsatisfiable at runtime, and the shopper would be the one to discover it.

A failure names the file, the row and the rule. StoreDataError is the only error in §12 that refuses to start.
